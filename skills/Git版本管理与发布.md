## 何时使用
用户要求把代码提交到 git 仓库、推送到 GitHub、或者打版本 tag 发布时使用。
所有实际操作都通过 `git_command` 工具执行，工具只支持有限的子命令，会改变仓库状态/
远程内容的操作（add/commit/push/pull/tag/checkout/init/clone）执行前都会弹出人工审核，
不用担心误操作。

## 重要区分：`git_command` 不受 MCP 文件访问白名单限制
`git_command` 和 `list_directory`/`read_file`/`edit_file` 等 MCP 文件工具是**两套完全
独立的访问机制**：
- MCP 文件工具受 `config.ALLOWED_DIRS` 白名单限制，只能访问用户主目录和默认工作目录，
  超出范围会报"不在允许访问范围"。
- **`git_command` 完全不受这个白名单限制**，`cwd` 参数可以是系统上任意路径（比如
  `F:\` 盘、`D:\` 盘），只要操作系统账号本身有权限访问就能正常执行。

**如果 `list_directory`/`read_file` 等 MCP 工具对项目目录报"不在允许访问范围"，
这只是这些工具自身的限制，绝不代表 `git_command` 也用不了、更不代表整个任务做不到**。
遇到这种情况，直接换用 `git_command` 继续操作，不要因为一个工具受限就下结论说
"无法访问这个目录"，也不要让用户去手动执行命令——`git_command` 本身就能处理任意路径。

**执行 git 相关任务时，第一步永远直接用 `git_command`，不要先用 `list_directory`/
`read_file` 之类的 MCP 工具去"探路"**——那样做不仅多余，一旦目录不在 MCP 白名单内还会
产生误导性的失败信息，让你误判成整个任务受限。

## 核心原则：不要硬编码任何仓库地址
**每个用户的仓库都不一样**，不要假设、不要编造仓库 URL。仓库地址必须来自用户明确提供的
信息，或者从当前目录已配置好的远程读出来（`git remote -v`）。如果用户说"帮我上传代码到
GitHub"但没给仓库地址，要先问清楚：仓库的完整 URL（例如
`https://github.com/<用户名>/<仓库名>`）。

## 步骤

### 1. 确认工作目录和仓库状态
1. 先确认要操作的项目目录（`cwd` 参数），没有明确说明就问用户。
2. **直接**用 `git_command(git_args="status", cwd=项目目录)` 看看是不是已经是 git
   仓库、有哪些变更——不要先用 `list_directory`/`read_file` 等 MCP 工具去检查目录
   是否存在，那些工具受路径白名单限制，`git_command` 不受限制，直接用它就够了。
3. 如果提示"not a git repository"，说明还没初始化：
   - 用 `git_command(git_args="init", cwd=项目目录)` 初始化。

### 2. 确认远程仓库
1. 用 `git_command(git_args="remote -v", cwd=项目目录)` 看有没有配置远程。
2. 如果没有配置，问用户要推送到哪个仓库（拿到完整 URL 后）：
   `git_command(git_args="remote add origin <用户提供的仓库URL>", cwd=项目目录)`
3. 如果已经配置好，直接用现有的 `origin`，不要重复添加或覆盖，除非用户明确要求换仓库。

### 2.1 发现仓库位置不符合预期时，先停下来问用户，不要自己决定
如果 `git status`/`git remote -v` 的结果显示"仓库是在父目录初始化的""这个目录不是
git 仓库根目录""远程已经有内容但本地历史跟它不一致"这类**跟预期不符**的情况，
**必须停下来，把发现的情况原样告诉用户，让用户决定怎么处理**（比如是重新
`init` 一个独立仓库、还是换个目录、还是接受现状继续），不要自己判断选一个方案就
直接往下执行。像"本地仓库历史跟远程完全不相关，需要合并"这种场景，**几乎必然会
产生冲突**，绝对不能在没有用户确认的情况下自己往下走 `pull`/合并。

### 3. 提交变更
1. **不要一上来就 `add .`**：先用 `git_command(git_args="status", cwd=项目目录)` 看清楚
   未跟踪/改动文件列表，确认里面没有明显不该入库的内容（编译产物如 `__pycache__/`、
   `.pyc`、临时文件、大体积二进制、看起来像密钥/凭据的文件等）。
   - 没有问题：`git_command(git_args="add .", cwd=项目目录)`（或者按用户要求只加特定文件）。
   - 发现有不该提交的文件：告知用户，问清楚是要排除这些文件（按需 `add` 指定文件而非
     `add .`，并建议用户补一个 `.gitignore`）还是确实要一起提交，不要自己直接决定忽略
     用户的疑虑硬 `add .`。
2. 提交信息要**说清楚这次改了什么、为什么改**，不要写"update"/"fix bug"这种空洞信息。
   参考格式：`<类型>: <一句话描述>`，类型可以是 feat/fix/refactor/docs/chore 等，例如：
   `git_command(git_args='commit -m "feat: 新增 Git 版本管理技能"', cwd=项目目录)`
3. 如果 `git status` 显示没有任何变更，直接告知用户"没有需要提交的内容"，不要强行提交。

### 4. 推送到远程
1. 第一次推送某个分支：
   `git_command(git_args="push -u origin <分支名>", cwd=项目目录)`（比如 `main`）。
2. 后续推送直接：`git_command(git_args="push", cwd=项目目录)`。
3. 推送失败（比如远程有新提交）时，把 git 返回的错误原文告知用户，不要自己臆测原因，
   也不要在没问过用户的情况下执行 `push --force`。

### 5. 打版本 tag 并发布
1. 先跟用户确认版本号，遵循语义化版本规范：`v主版本.次版本.修订版本`（比如 `v1.0.0`）。
2. 打 tag：`git_command(git_args='tag -a v1.0.0 -m "Release v1.0.0"', cwd=项目目录)`。
3. 推送 tag：`git_command(git_args="push origin v1.0.0", cwd=项目目录)`。
4. 推送完 tag 之后告知用户：如果仓库在 GitHub 上，可以去仓库的 Releases 页面基于这个
   tag 手动创建正式 Release（写更新日志），或者如果用户本机装了 GitHub CLI（`gh`），
   也可以在确认好版本号和说明文字后手动执行 `gh release create v1.0.0`
   （这一步不在 `git_command` 的支持范围内，需要用户自己在终端执行，或明确要求扩展
   支持后再加）。

## 6. 遇到合并冲突怎么处理
`pull`（或 `merge`）如果返回结果里出现 `CONFLICT`，说明产生了合并冲突，`git_command`
会在结果里附加醒目提示,并告知有没有自动打的安全快照 tag（`presync_<时间戳>`）。
这时**必须严格按下面顺序处理，不允许跳过任何一步**：

1. **绝对不能直接 `add`/`commit`**——`git_command` 已经在代码层面做了硬性拦截：
   只要检测到还有未解决冲突的文件，`add`/`commit` 会直接被拒绝执行，不会真的跑。
   看到"检测到以下文件存在未解决的合并冲突"这条返回信息时，不要重复尝试 `add`，
   而是按下面的步骤先处理内容。
2. 用 `read_file` 读取冲突文件的**完整内容**，找到 `<<<<<<< HEAD` ... `=======` ...
   `>>>>>>>` 这几段标记。
3. 根据两边的内容判断怎么合并：如果能明显看出该保留哪一部分，直接合并出干净版本；
   如果看不出来，**必须问用户想保留哪一边**，不要自己猜。
4. 用 `write_file` 把合并好的、**不含任何 `<<<<<<<`/`=======`/`>>>>>>>` 标记**的干净
   内容写回原文件。写完之后最好再用 `read_file` 确认一遍，确保标记确实清干净了。
5. 确认所有冲突文件都处理完后，才能重新 `add`/`commit`。
6. 如果用户想直接放弃这次合并（不想手动解决冲突），可以用安全快照恢复：
   `git_command(git_args="reset --hard <safety_tag>", cwd=项目目录)`，把仓库恢复到
   合并之前的状态。

## 禁止事项
- 不要凭空编造仓库地址、分支名、提交信息。
- 不要在未询问用户的情况下执行 `push --force`、覆盖远程分支、或删除 tag。
- 遇到冲突/推送被拒绝，如实告知报错内容，让用户决定怎么处理，不要自己尝试"绕过"冲突。
- 不要使用 `--allow-unrelated-histories` 强行合并两段不相关的历史（`git_command` 会
  直接拒绝这个参数）；发现本地/远程历史不一致时，按 §2.1 停下来问用户。
- 冲突未处理干净之前，不要重复尝试 `add`/`commit`，也不要绕开 `read_file`/`write_file`
  去"猜"内容该怎么改。
